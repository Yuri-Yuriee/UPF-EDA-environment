# TECH_MV Verify Environment

This environment intentionally combines two references:

- **HDL_verify**: directory organization, Makefile-driven workflow, clean targets,
  and the idea of generating Hcell information instead of maintaining it by
  hand.
- **TECH_verify**: TECH 9M Calibre deck paths, Dummy/DRC/Antenna execution
  sequence, LVS deck handling, and TECH PDK/Virtuoso setup.

No REFERENCE_PLATFORM deck/library path is used.

## Quick start

From `TECH_MV/`:

```bash
make verify_check
make verify_hcell
make verify
```

or from `TECH_MV/verify/`:

```bash
make check
make hcell
make lvs
make dummy
make drc
make antenna
make status
```

One-command full flow:

```bash
make signoff
```

## Output auto-detection

The verify scripts first honor:

```csh
setenv VERIFY_OUTPUT_DIR /your/output/path
```

If it is not set, they look for:

1. `TECH_MV/outputs/CHIP.gds`
2. `<project>/build_PR/outputs/CHIP.gds`

This matches the normal TECH_MV master/runtime split.

## Hcell / LVSBOX

The LVS flow supports two explicit modes. `VERIFY_HCELL_MODE` defaults to `ON`.

```csh
# Hcell mode ON: generate/use HCELL + LVSBOX
setenv VERIFY_HCELL_MODE ON
make lvs

# Hcell mode OFF: do not generate/use HCELL or LVSBOX
setenv VERIFY_HCELL_MODE OFF
make lvs
```

Convenience targets are also provided:

```text
make lvs_hcell
make lvs_nohcell
```

In `ON` mode, `HCELL` is copied to the local LVS scratch directory and passed
to Calibre with `-hcell ./HCELL`. In `OFF` mode, neither the explicit HCELL
file nor the generated `LVS BOX` statements are used. The actual mode used for
each run is recorded in `lvs/rpt/lvs_mode.rpt`.


```bash
make hcell
```

generates:

```text
lvs/HCELL
lvs/LVSBOX
lvs/rpt/hcell_generation.rpt
```

from the **current TECH_MV LEF set**.

The generator follows the supplied TECH method and excludes physical-only:

```text
FILL_IN_CELL_BOND_PAD_041
- Physical-only Cell exclusions are configured in `config/hcell_policy.tcl`.
BOUNDARY_*
FILL*
PFILL*
TAP*
```

When `VERIFY_HCELL_MODE=ON`, `LVSBOX` is automatically inserted into the
generated LVS runset. It is no longer necessary to maintain thousands of
`LVS BOX` lines by hand. In `OFF` mode those generated box statements are not
inserted.

## LVS source include

```bash
make source_inc
```

generates `lvs/CHIP_inc.spi`.

- Core/IO SPICE paths come from the supplied TECH_verify reference.
- Current TECH_MV LVL/PM source files are resolved by runtime glob.
- Current TECH_MV SRAM source files are discovered below each compiler root.
- TECH PDK `source.added` is included.
- `CHIP.spi`, generated by v2lvs, is included last.

If a required source cannot be resolved, generation stops with the missing
library name/path instead of silently running an incomplete LVS.

## Dummy / COD

The supplied TECH_verify flow requires:

```text
BEOL
COD
FEOL
MERGE
```

The older TECH_MV verify tree was missing COD. It is restored here.

The merged GDS is:

```text
add_dummy/CHIP_adddummmy.gds.gz
```

The filename is intentionally retained because it is the validated TECH
reference filename used by DRC/Antenna.

## LVS result note

The supplied `TECH_verify` archive demonstrates that the TECH LVS command/deck
setup executed successfully, but its archived log ends with:

```text
LVS completed. INCORRECT.
```

Therefore this integration treats that reference as a validated **execution
method/path reference**, not proof that the old example design passed LVS.

Use `make status` to inspect the result produced by the current TECH_MV design.

## No `drc_be`

The old TECH_MV verify inherited an REFERENCE_PLATFORM-oriented `drc_be` target. The supplied
TECH reference does not use that flow, so it has been removed instead of
guessing a TECH replacement.

## Runtime location

The master Verify environment stays in:

```text
script/PR/TECH_MV/verify/
```

Normal top-level execution copies it to:

```text
build_PR/verify/
```

and runs LVS / Dummy / DRC / Antenna there. APR results stay in:

```text
build_PR/outputs/
build_PR/dbs/
```

Useful cleanup commands:

```bash
make clean_verify
make reset_verify_flow
make clean_innovus_keep_results
```

`clean_verify` removes generated Verify results but keeps the copied Verify
environment. `reset_verify_flow` removes the complete `build_PR/verify` runtime.
`clean_innovus_keep_results` cleans the rest of `build_PR` while preserving
`outputs`, `dbs`, and the copied Innovus environment.

## Fixed TECH signoff collateral

The Verify environment uses the installed TECH 9-metal collateral directly:

```text
LVS:
<configured private resource>
<configured private resource>

DRC / Antenna / Dummy:
<configured private resource>
```

The `iPDK_10m_*`, `*_SNPS`, online variants, and PDK patch copies are not used
by default.

`CHIP.gds` and `CHIP_pg.v` remain design outputs from `build_PR/outputs/`; they
are not foundry collateral.
## tcsh pipeline status compatibility

Verify commands are logged through `common/run_logged.sh`, which uses Bash
`pipefail` to preserve the EDA tool exit code while still mirroring output with
`tee`. This avoids the non-portable tcsh `$pipestatus` variable.



## Terminal summary and DRC dummy gate

The Verify flow now prints a terminal summary after LVS and after the major
signoff stages.

DRC and Antenna are hard-blocked unless all dummy stages have completed:

- BEOL
- COD
- FEOL
- MERGE

The final DRC input must be `add_dummy/CHIP_adddummmy.gds.gz`. The guard also
rejects a final dummy GDS that is older than the raw APR GDS or any dummy
component GDS.

`LVS completed` is reported separately from correctness. For example,
`LVS completed. INCORRECT` is summarized as `LVS : INCORRECT` rather than PASS.

## Verify output hygiene (2026-10-11)

Normal Makefile execution stages the modified foundry decks and generated runsets
under each stage's `temp/` and removes those named files after the child command
finishes, on success or ordinary failure. Original installed decks are untouched.
DRC/Antenna/Dummy summary reports go to `rpt/`; logs go to `log/`. Result databases,
LVS reports/SVDB, source netlists, dummy GDS and `.stage` completion markers are
retained because consumers need them. Calibre deck commands which generate fixed
GDS names retain their established working directory; those names are not changed.

From the project root:

```sh
make clean_verify_sensitive_preview
make clean_verify_sensitive
```

These remove only explicitly named deck/runset copies and optional extracted
`lvs/layout.spi` / `lvs/temp/layout.spi`, preserving reports, logs and history.
Existing `make clean_verify` still removes all generated Verify results.
Cleanup rejects symlinks and refuses to run while a Makefile stage is active.
Calling a stage `.csh` directly bypasses automatic cleanup; use the Makefile or
run `make clean_sensitive` from this directory afterwards. SIGKILL or a machine
crash can also leave staging files; the explicit cleanup target handles these.

LVS does not copy the scratch `layout.spi` into the project by default. For
explicit debugging, export `VERIFY_COPY_LVS_LAYOUT_SPICE=1`; it is copied to
`lvs/temp/layout.spi` and kept until explicit sensitive cleanup. To reuse the
extraction in `lvs_debug_nobody`, also export `VERIFY_KEEP_LVS_STAGING=1` during
normal LVS; that explicit debug option preserves the LVS deck/runset in `temp/`. Failed LVS
scratch is preserved for debug under the existing scratch policy.

New runtimes are created from `common/runtime_sources.json`, without copying
old reports, databases, decks, generated runsets or archives. Source changes
are not silently propagated into an existing runtime. Both current TECH_MV
Verify source trees were synchronized and tested using mock tools; this does
not constitute a Calibre signoff validation.
